Writing a bug report

What makes a report easy to fix.

A one-line message like "the PDF tool doesn't work" is still better than nothing, but it usually takes three emails to figure out what happened. A good report saves that. Here is the short version of what helps.

Include these four things

  1. The tool name. "Compress PDF" or "JSON Formatter", not just "your site." There are a lot of tools here and the name narrows it down instantly.
  2. The browser and device. "Chrome on Windows" or "Safari on an iPhone" is enough. Some bugs only show up on one engine, and knowing the browser is the fastest way to reproduce them.
  3. What you expected, and what happened. "I uploaded a 5 MB PDF and expected a compressed download. The button spun for a minute and nothing happened" is a complete report. That gives me something to chase.
  4. A screenshot, if you can. Not required, but a screenshot of an error message is often the difference between a fix in one attempt and a fix in three.

Setting expectations

What actually happens after you send a message.

I am one person doing this in the evenings, so I would rather be honest about what the follow-up looks like than pretend every message gets a same-day reply.

What you can expect

  • Every message gets read. Even if a reply takes a while, the inbox is checked and nothing is ignored.
  • Genuine bugs get fixed. Sometimes the same day. Sometimes a few weeks later, when there is time to sit with it.
  • Suggestions get considered on their merits. Not because someone asked louder, but because the tool would be useful and fits the site.
  • Credit if you want it. Some people like a small "suggested by" line on the tool page. Some do not. Either is completely fine.

What might not happen

  • Every suggestion, built. Some ideas are outside what a browser can do, or are already well served elsewhere. I would rather say that than promise something I cannot deliver.
  • A same-day reply. This is not a full-time job. Replies are usually within a week, sometimes longer.
  • A "we'll consider it" email. If the answer is no, the answer is no. I will tell you briefly rather than send filler.
  • A guaranteed timeline. A fix might land in a day or in a month. It depends on what else is on the list.

Common questions

Support FAQ

Do I need to pay or subscribe to get support?

No. There is no payment anywhere on the site. Support here means help with a bug or a suggestion, and it is the same for everyone. No tier, no priority line.

How fast will I hear back?

Usually within a week. This is a solo project, not a full-time job, so replies can be slow. But every message does get read.

Will every suggested tool get built?

No, and I would rather say that up front. Some ideas are outside what a browser can do. Some are already well served elsewhere. The ones I can build and that fit the site are the ones that get built. If your idea is a no, you will hear why.

What should a bug report include?

The tool name, the browser you were using, what you expected to happen, and what happened instead. A screenshot is helpful if you can take one. The longer version is above.

Can I suggest a tool that does not exist yet?

Yes, and some of the tools on the site started that way. Describe the task you are trying to do, not just the name of a tool, and it is easier to figure out whether it fits.

Is there a way to send feedback that is not a bug report?

Yes. A short note about what worked, or what confused you, is genuinely useful. It is a solo project and the inbox is quiet, so those messages get read carefully.

What if I want to help some other way?

Email me and we can talk about it. Sometimes people offer to help with translations, or with testing on a browser I do not have easy access to. I would not turn down the help, but I would want to be clear about the scope first.
