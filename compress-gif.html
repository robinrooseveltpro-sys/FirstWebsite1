How to compress a GIF without losing the animation

A GIF is not a video. It is a stack of full images, each with its own colour table and its own delay. That structure gives you four independent levers, and the order you apply them determines whether the result still looks like the original.

Applied in the wrong order, compression produces a jerky, colour-banded mess. Applied in the right order, most GIFs shrink by 50–80% with barely any visible change.

The four levers, in order of least visible damage

LeverWhat it doesVisible cost
Lossy matchingPixels that barely changed since the last frame are written as transparent, so they compress as one long runVery low at light settings; subtle smearing at strong settings
Palette reduction256 colours → 128 → 64 → 32 → 16 per frameBandng in gradients and photos; fine for flat-colour animations
ResizingHalving width and height keeps a quarter of the pixelsSofter edges; usually the biggest size win
Frame droppingEvery 2nd or 3rd frame removed, delays mergedJerkier motion — and faster playback if delays are not rescaled

The bug that most GIF compressors ship

When gifsicle drops frames, it removes them from the stream but leaves the remaining delays untouched. A 17.4-second loop that keeps every second frame then plays in 8.75 seconds — the animation runs at double speed. This is documented behaviour, not a rare edge case: a 2026 write-up on gifsicle's knobs noted that “the 17.41 s loop played in 8.75 s and the cat wagged at double speed.”

This tool fixes it. When frames are dropped, it computes the original total duration from the GIF's own graphic-control blocks, divides by the new frame count, and passes a uniform delay so playback time is preserved. The animation gets jerkier, never faster. The toggle is on by default; turn it off only if you specifically want a faster loop.

Why fewer colours can make a GIF bigger

It sounds counter-intuitive, but reducing the palette does not always reduce the file. If a GIF was already optimised with a tuned palette and lossy frame matching, forcing it down to 32 or 16 colours can destroy the inter-frame similarity that lossy matching relies on, so more pixels change between frames and the file grows. A 2026 test documented exactly that: fewer colours made an already-optimised GIF 91% bigger.

This tool re-measures after every ladder step rather than assuming a step helped. If a palette reduction produces a larger file, that result is discarded.

GIF vs MP4 vs WebP — when to stop using GIF

GIF is a 1987 format with a hard 256-colour limit and no inter-frame motion compensation. A modern MP4 or WebP version of the same animation is typically 5–20× smaller at higher visual quality. If your destination supports video or WebP — and most modern platforms do — compressing the GIF is treating the symptom, not the cause. Use this tool when the destination requires GIF: forums, older chat clients, documentation, and sites that reject video embeds.

Size targets

How do I compress a GIF to 256 KB?

Type 256 in the target field — or click the 256 KB chip — and press Compress GIF. The tool walks the priority ladder from gentle lossy compression up to palette reduction, resizing, and frame dropping, stopping at the first step whose output is under 256 KB. The result keeps the animation; only the last two ladder steps touch frame count.

What is Discord's GIF size limit, and how do I fit under it?

Discord's standard upload limit is 10 MB for non-Nitro accounts, though some servers set it lower. Click the Discord preset to set a 10 MB target. Most GIFs under a minute long will fit at the first or second ladder step, so you keep full frame rate and the original palette.

What limits do Slack and WhatsApp use for GIFs?

Slack's free plan caps uploads at 5 MB. WhatsApp's media limit is 16 MB, but large GIFs are often recompressed or converted to short video on send, so a 16 MB GIF may not arrive intact. The Slack and WhatsApp presets set 5 MB and 16 MB respectively.

Can I compress a GIF to 512 KB or 1 MB?

Yes — the chips cover 100 KB, 256 KB, 512 KB, 1 MB, 5 MB, and 10 MB, and the numeric field accepts anything from 10 KB to 50 MB. The ladder is the same regardless of the number; only the stopping point changes. A 1 MB target usually resolves at step 3 or 4, leaving the palette and frame rate intact.

Why does the result land slightly under my target instead of exactly on it?

The target is a ceiling, not a fixed size. The tool stops at the first ladder step that fits, so the result is always at or below your number — sometimes by a wide margin if one step overshoots. Chasing the exact byte count would require many more encode passes for a difference you cannot see.

Animation & playback speed

Does compressing a GIF remove the animation?

No. The animation is preserved at every ladder step. Only the last two steps — used when gentler options cannot reach your target — reduce the frame count, and even then the remaining frames still animate. A static GIF stays static; an animated GIF never becomes a single frame.

Why do some compressed GIFs play at double speed?

Because gifsicle removes frames but leaves the delays on the remaining ones unchanged. Keep every second frame and the total playback time halves, so the animation appears to run at 2×. It is a real, documented behaviour of the tool, not a rendering quirk. This compressor rescales the delays whenever it drops frames, so the loop keeps its original duration.

What does the "Preserve playback speed" toggle actually do?

When frame dropping is used, the tool reads the original GIF's total duration from its graphic-control blocks, divides by the new frame count, and writes a uniform delay. The animation becomes jerkier because there are fewer frames, but a 10-second loop still takes 10 seconds. Turn the toggle off only if you deliberately want a faster loop.

Will frame dropping make the animation play backwards or stutter?

It cannot play backwards — frames are removed in order, not reordered. Stutter is the correct expectation: keeping every second frame halves the frame rate, so motion looks steppier. That is the visible cost of the largest size saving available, which is why it sits near the bottom of the ladder.

Does the compressed GIF keep its original loop count?

Yes, by default. The "Preserve loop count" option is on, so an infinitely looping GIF keeps looping instead of being flattened to a single play. Turn it off only if you want a one-shot version.

Quality & palette

What is lossy GIF compression?

GIF itself is lossless, but gifsicle supports a lossy extension: pixels that barely changed since the previous frame are written as transparent instead of being re-encoded. Because a run of identical transparent pixels compresses to almost nothing, the file shrinks — at the cost of slight smearing in detailed areas. Light settings are often invisible; strong settings are not.

Why did reducing colours make my GIF bigger?

Palette reduction can destroy the inter-frame similarity that lossy matching depends on. If a file was already optimised with a tuned palette, forcing it to 32 or 16 colours makes more pixels change between frames, so the file grows. A documented 2026 test saw a 91% increase. This tool measures after every step and discards a step that made the file larger.

How many colours should I keep?

Start by leaving the palette alone. Flat-colour animations — cartoons, UI recordings, text — survive 32 or even 16 colours well. Photographic GIFs and anything with gradients will band visibly below 128 colours. The automatic ladder handles this; in manual mode, try one step at a time and compare the preview.

Is resizing better than palette reduction?

Usually yes, for photographic content. Halving width and height removes three-quarters of the pixels, which shrinks the file dramatically while producing softness rather than banding. For flat-colour art, palette reduction is often less noticeable than a resize. The ladder tries palette reduction before resizing because it is less destructive on the common case.

GIF vs MP4 vs WebP

Should I convert my GIF to MP4 instead?

If your destination accepts video, almost always yes. MP4 uses inter-frame motion compensation and a modern codec, so the same animation is typically 5–20× smaller at higher quality. Discord, Slack, and most social platforms accept MP4. Use this compressor when the destination requires GIF specifically.

Is WebP a better format than GIF for animations?

Yes for size and quality — animated WebP supports 24-bit colour and alpha, and files are usually far smaller. Support is now broad in browsers, but some older chat clients and forums still reject WebP. If your destination is modern, animated WebP is the better target; if it is not, GIF is the safe choice.

Why does a GIF have a 256-colour limit?

The format stores each pixel as an 8-bit index into a palette, which allows exactly 256 entries per frame. That was generous in 1987 and is very restrictive today. It is the main reason GIF files are large relative to their visual quality — the format cannot use colour similarity as efficiently as a modern codec.

Failures & limits

What happens if my target size cannot be reached?

The tool reports the smallest result it achieved and shows it in the preview, rather than pretending to succeed. You then have three options: raise the target, accept the smallest result, or convert to MP4 or WebP, which will usually reach the target easily. The message states which step produced the result.

Why does compression take longer on large GIFs?

gifsicle's optimisation passes scale with frame count and pixel count. On files above roughly 10 MB, higher optimisation levels become exponentially slower for almost no additional saving — which is why this tool uses -O1 deliberately and warns you above 10 MB rather than silently hanging.

Does this work offline?

After the first load, yes. The gifsicle WASM module is cached by the browser, and all compression happens locally. You can disconnect from the network and compress further files in the same session.

Why is there a loading delay the first time?

The gifsicle WebAssembly module is around a megabyte and is fetched only when you press Compress GIF, not on page load. That keeps the page fast for visitors who are only reading. After the first use it is cached and subsequent compressions start immediately.

Privacy & how it works

Is my GIF uploaded to a server?

No. gifsicle is compiled to WebAssembly and runs inside your browser tab. The file is read with the File API, processed in memory, and offered back as a download. Nothing is transmitted. You can verify this in your browser's network tab — the only request is for the WASM module itself, not your file.

Is there a watermark or a file-count limit?

No watermark, no signup, no daily cap, no subscription. The downloaded GIF is a normal GIF with no added branding.

Does this tool store my GIF anywhere?

No. The file exists only in the page's memory for the current session. Nothing is written to localStorage, cookies, or a server. Closing the tab discards everything.

Is my GIF safe to process here?

Processing is local, so the file never leaves your device. The only external resource the page loads is the gifsicle WebAssembly module from a public CDN, which contains no user data. If you need to process files in an air-gapped environment, the module can be self-hosted alongside the page.
