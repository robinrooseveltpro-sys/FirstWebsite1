What this tool checks and what it does not

  • Checks: that DNSKEY records exist at the zone apex, that DS records exist at the parent, and that at least one DS digest cryptographically matches a DNSKEY in the zone. That last check is real SHA-1, SHA-256, or SHA-384 verification done in your browser.
  • Checks: that RRSIG records are present at the apex, which signer names they come from, and whether their validity window has expired.
  • Does not check: cryptographic validity of the RRSIG signatures themselves. Verifying a signature requires canonical wire-format ordering of every RRset and per-algorithm signature verification. If you need that, use the ICANN DNSSEC Debugger (dnsviz.net) or the bondit.dk validator.
  • Does not check: the chain of trust from the root. A zone can have a matching DS-to-DNSKEY pair and still fail to chain if the parent zone is itself unsigned or misconfigured. This tool shows you the DS at the immediate parent, not the full path to the root.
  • Does not check: subdomains. It checks the zone apex only. If you entered www.example.com, the tool walks up to the apex (example.com) and checks that zone.
  • Public DNS-over-HTTPS endpoints rate-limit. If checks start failing, wait a minute and retry, or switch resolvers.

What is DNSSEC?

DNSSEC adds cryptographic signatures to DNS records so that a resolver can prove the answer it received came from the real owner of the zone and was not tampered with in transit. Without DNSSEC, DNS is trust-on-first-response: anyone on the network path can forge an answer. With DNSSEC, each zone signs its records and each parent zone vouches for the child zone's signing keys.

How does this tool check a domain?

It queries three record types: DNSKEY at the zone apex, DS at the zone apex (which is actually served by the parent zone), and RRSIG at the apex. It then computes the DS digest from each DNSKEY using the digest type listed in the DS record, and compares that digest to the DS digest. If they match, the DNSKEY at the zone is provably the one the parent said should be there. If they do not match, the zone is signed but chained to the wrong key, which is a misconfiguration.

What is the chain of trust?

DNSSEC works by delegation. The root zone signs the DS records for each TLD. Each TLD signs the DS records for each registered domain. Each registered domain signs its own DNSKEY and other records. When a resolver looks up a domain, it follows this chain from the root down, verifying each link. If any link is broken, DNSSEC validation fails, and depending on the resolver's policy, the answer is either refused or accepted but flagged as insecure.

What is a DS record and why does it matter?

A DS record is published by the parent zone. It contains a hash of the child zone's DNSKEY, plus the algorithm and key tag of the key it corresponds to. When the child zone rotates its keys, it must coordinate the DS update with the parent, or validation breaks. A DS record at the parent that does not match any DNSKEY at the child is the most common cause of sudden DNSSEC outages, usually after a key rollover that was not coordinated with the registrar.

What is an RRSIG and why doesn't this tool verify it?

An RRSIG is a cryptographic signature over a DNS record set. Verifying it correctly requires reconstructing the RRset in canonical wire format, which means exact byte ordering, exact TTL, and per-algorithm signature verification. Doing this correctly in a browser is a substantial amount of cryptographic code, and getting it wrong in a security context is worse than not doing it. This tool shows RRSIG records, their signer, key tag, and validity window, and flags expired signatures, but it does not cryptographically verify the signature. For that, use dnsviz.net or dnssec-validator.bondit.dk.

What does "DS matches DNSKEY" mean?

It means the cryptographic hash of the DNSKEY record, computed with the digest type declared in the DS record, equals the digest value in the DS record. That is the exact check a resolver performs when following the chain of trust from parent to child. If it matches, the parent's DS is vouching for that DNSKEY and the child zone is correctly chained. If it does not match, either the DNSKEY has been rotated without updating the DS, or the DS has been updated without rotating the DNSKEY to match.

What is an island of trust?

An island of trust is a zone that is signed with DNSSEC and whose own DS-to-DNSKEY chain is internally consistent, but whose parent zone does not publish a DS record for it. That means the zone is signed, but the chain from the root stops at the parent. Resolvers will treat the zone as insecure, which means DNSSEC validation is not enforced. The fix is to publish the DS record at the registrar, which propagates it to the parent zone.

How do I fix a DNSSEC configuration error?

For a mismatch between DS and DNSKEY, the fix depends on which side is wrong. If you recently rotated keys at your DNS host, you need to update the DS at your registrar to match the new DNSKEY. If you recently updated the DS at the registrar without rotating keys, you need to either roll the DNSKEY back or complete the rollover. Check your DNS provider's documentation first, because some providers manage the DS update automatically and some do not. For a missing DS on a signed zone, publish the DS at your registrar. For a DS on an unsigned zone, remove it, because a DS pointing to a nonexistent DNSKEY is worse than no DNSSEC at all.

What algorithm numbers do I see in the results?

Common values: 8 is RSASHA256, 13 is ECDSAP256SHA256, 14 is ECDSAP384SHA384, 15 is ED25519, 5 is RSASHA1 (deprecated), 7 is RSASHA1-NSEC3-SHA1 (deprecated), 1 is RSAMD5 (obsolete, do not use). Algorithm 13 is the current default for new deployments. Digest types you may see in DS records: 1 is SHA-1 (deprecated but still in use), 2 is SHA-256 (current default), 4 is SHA-384.
