The five fields, in order

A cron expression has five fields separated by spaces. The order is fixed and does not change between Unix, Linux, macOS, GitHub Actions, or Kubernetes. Reading left to right:

  1. Minute, 0 to 59
  2. Hour, 0 to 23 (not 1 to 24)
  3. Day of month, 1 to 31
  4. Month, 1 to 12
  5. Day of week, 0 to 7 (0 and 7 are both Sunday)

The expression 0 9 * * 1-5 means "minute zero, hour nine, any day of month, any month, Monday through Friday". In plain English, weekdays at 9am.

The two mistakes that break most cron jobs

Midnight is 0 0, not 0 24. The hour field runs from 0 to 23. There is no hour 24. An expression that says 0 24 * * * is rejected by most cron implementations because 24 is out of range, and the ones that accept it treat it in ways that are inconsistent between platforms. If you want midnight, use 0. If you want one minute past midnight, use 1 0. If you want 11pm, use 23.

Day of month and day of week are not combined the way you think. When both fields are restricted (neither is *), cron matches if either one matches, not both. So 0 0 1 * 1 fires on the first of the month AND on every Monday, because the DOM matches on the 1st and the DOW matches on Mondays. If you want "the first Monday of the month", cron cannot do it with a single expression, and you need to write the logic in the script itself. This is the single most common reason a cron job fires on a day the author did not expect.

On ranges and steps. A range is written 1-5 and means every value from 1 to 5 inclusive. A step is written */15 and means every 15th value starting from the minimum. A range with a step is written 0-30/5 and means every 5th value from 0 to 30. A list is written 1,3,5 and means exactly those values. These combine, so 0-30/5,45 means every 5 minutes from 0 to 30, plus minute 45.

Where cron runs, and where it differs

The classic Unix cron runs on a server and reads from the user's crontab. It runs in the server's local time zone, which matters because a cron expression that says "9am" fires at 9am in whatever time zone the server is set to, not in yours. If you write a cron on your laptop for a server in UTC, the job fires at 9am UTC, not 9am local.

GitHub Actions uses cron syntax but runs in UTC only. There is no way to set the time zone. So a job that you want to run at 9am New York time is 0 13 * * * during daylight saving and 0 14 * * * during standard time. The tool on this page shows the next run times in your browser's local time zone, which is why the "next runs" panel and the "run time" line on the reference card can disagree if you are in a non-UTC time zone.

Kubernetes CronJob uses the same five fields, runs in UTC by default, and lets you set the time zone with the timeZone field in the manifest on newer versions. Systemd timers do not use cron syntax at all; they use a calendar-style syntax that is similar but not identical. If you are scheduling a systemd timer, a cron expression is not the right tool.

Basics

What does * * * * * mean?

Every minute of every hour of every day of every month. It is the most frequent schedule cron can express, and it is almost never what you actually want on a production system. Running every minute on a shared server is a fast way to fill a log file or hit an API rate limit.

What does 0 0 * * * mean?

Midnight every day. Minute 0 of hour 0, any day of month, any month, any day of week. If you see an expression with 24 in the hour field, that is wrong on most implementations; midnight is 0, not 24.

What is the difference between 0 and 7 for Sunday?

Both mean Sunday in standard cron. The day-of-week field runs from 0 to 7, where 0 is Sunday, 1 is Monday, and so on to 6 is Saturday, and 7 wraps back to Sunday. Some systems accept 7, some reject it. If you want Sunday, use 0; it works everywhere.

How do I run something every 5 minutes?

*/5 * * * *. The */5 in the minute field means "every 5th value starting from 0", which gives 0, 5, 10, 15, up to 55. If you want every 5 minutes starting from a specific offset, use 2-59/5 and the runs will be at 2, 7, 12, and so on.

Does cron support seconds?

Standard Unix cron does not. The five-field format has a resolution of one minute. Some implementations (Quartz in Java, some AWS services) accept a six-field format with seconds at the front, and some accept */10 in a seconds field to run every 10 seconds. If you are using a system that supports seconds, this tool will not generate the six-field format; you would need to add the seconds field yourself. The five-field format is the most portable and is what this tool targets.

Common mistakes

Why does my cron job run on days I did not expect?

Almost certainly because both the day-of-month and day-of-week fields are restricted. When both are restricted, cron matches if either one matches, not both. So 0 0 1 * 1 fires on the first of the month AND on every Monday, not on "the first Monday". If you want a combined condition, you cannot do it with the expression alone; the script has to check the current date and exit if it is not the right day.

Why does my cron job run at the wrong time?

The most common reason is that the server's time zone is not your time zone. Cron runs in the local time of whatever system the crontab is on, and servers are usually set to UTC. A job that says 0 9 * * * fires at 9am UTC, which is 4am or 5am on the US east coast. If you want 9am local, either set the server's time zone or adjust the hour in the expression to match UTC.

Why is my cron job not running at all?

Three common causes. First, the crontab was edited but not saved, or the cron daemon was not reloaded. Second, the script does not have the execute permission or the shebang line is wrong. Third, the script relies on environment variables (PATH is the usual culprit) that cron does not set the same way your interactive shell does. Cron runs with a minimal environment; if your script uses node or python without an absolute path, it may fail silently because cron's PATH does not include the directory where those binaries live.

Can I use names instead of numbers for months and days?

Yes on most implementations. 0 0 * jan * and 0 0 * * mon both work in the standard Vixie cron and its descendants. The names are case-insensitive and the first three letters are enough. This tool accepts the aliases in the Explain tab and normalises them; the Build tab produces the numeric form because it is more portable.

Platforms

Does this work for GitHub Actions?

The syntax is the same five fields, but GitHub Actions always runs in UTC and does not accept a time zone. A cron you write for 9am local time has to be adjusted to 9am UTC, which is a different hour depending on the season. If you want a job that fires at a fixed local time regardless of daylight saving, you cannot do it with the schedule trigger alone; you need to either trigger on a broader window and check the time inside the job, or use an external scheduler.

Does this work for Kubernetes CronJob?

Yes, the five-field syntax is the same. Kubernetes runs in UTC by default. On newer versions (1.27+), you can set timeZone in the CronJob spec to use a named time zone. If your cluster is older, you cannot set the time zone, and the schedule fires in UTC.

Does this work for systemd timers?

No. Systemd uses a different calendar syntax called OnCalendar, which looks similar but is not compatible. A systemd timer expression like Mon..Fri 09:00 means weekdays at 9am, and it does not use the five-field format at all. If you are scheduling a systemd unit, this tool is not the right fit.

What about Windows Task Scheduler?

Windows Task Scheduler does not use cron syntax. It uses a graphical interface and XML task definitions. There are cron-to-Task-Scheduler translators online, but this tool does not produce that format.

Time zones

What time zone does the next-runs panel use?

Your browser's local time zone. The tool reads the current time and shows the next five matches in that zone. If you want to see the runs in UTC, set your browser's time zone to UTC temporarily, or check the server that will actually run the job; that server's time zone is what matters, not yours.

How do I make cron use a specific time zone?

On a Unix server, you set the system time zone (usually via /etc/timezone or timedatectl), and cron inherits it. There is no per-crontab time zone in standard cron. If you need per-job time zones, you cannot get them from cron alone; you either adjust the expression or move the job to a scheduler that supports time zones (Kubernetes 1.27+, or a managed scheduler like EventBridge Scheduler or Cloud Scheduler).

Does cron handle daylight saving time?

Yes and no. Cron runs on the system clock, so when the system clock changes for daylight saving, the schedule follows. This can cause surprising behaviour: a job scheduled at 2:30am local time on the day the clocks go forward does not run, because 2:30am does not exist that day. A job scheduled at 1:30am on the day the clocks go back runs twice, because 1:30am happens twice. If the job has side effects, it needs to be idempotent or the script needs to check whether it has already run.

Limits

Does the plain-English input handle everything?

No. It handles the common patterns: "every N minutes", "every N hours", "every weekday at TIME", "every DAYNAME at TIME", "monthly on the Nth", "daily at TIME", and the special strings (@daily, @hourly, etc.). For anything more complex, use the field inputs, which accept the full cron syntax including ranges, lists, and steps.

Does the tool validate against a real cron daemon?

It parses the expression against the standard five-field rules and shows next run times computed from those rules. That is the same logic a cron daemon uses, but it is not a daemon itself. Some implementations have small differences (for example, whether 7 is accepted as Sunday, or whether a step on a range is inclusive). If your expression works in this tool and the schedule looks correct, it will work on the standard cron, but if it is failing on a specific server, the difference is in the implementation, not the expression.

Does the tool store my expression anywhere?

No. Everything happens in the browser. There is no local storage, no server call, no analytics event tied to what you typed. When you close the tab, the expression is gone. The Copy button puts it on the clipboard; that is the only place it goes.
